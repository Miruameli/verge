### Release contents

Version bump only: workspace `0.3.0` → `0.4.0`, regenerated `Cargo.lock`,
CHANGELOG `[Unreleased]` → `[0.4.0]` with a `Migration` section. The single
breaking API change is `TagEntry` (3-tuple → named struct
`{ name, commit, table, summary }`); `VergeError::CommitBelongsToOtherTable`
is a new variant on a `#[non_exhaustive]` enum and needs no migration.
`verge-cli` is installable from the registry for the first time; the binary
stays named `verge`.

### Compliance notes

- The tag points at commit `602bd23` on `main`, already green on all six CI
  checks (PR #74).
- Failure-prone steps ran before irreversible ones: bump merged → tag →
  release run green → core publish → sparse-index poll → CLI publish.
- The `publish-crate` manifest gate refused nothing: bump + lock landed in the
  same merged PR, so `--locked` held at upload.

### Evidence

- The `release.yml` workflow on tag `v0.4.0` finished with `success`; run
  `37439510268`.
- `sha256sum -c --strict SHA256SUMS` accepted all files after re-downloading
  them from the GitHub Release.
- The `aarch64-unknown-linux-gnu` binary from the release runs a real flow:
  `init → import → commit → log → show HEAD → tag create → tag list`.
  `verge --version` reports `verge 0.4.0`; `tag list` prints
  `smoke-tag <id> users smoke 0.4.0`.
- Pre-publish `cargo package` proved the ordering rule, not a defect:
  `verge-core` packaged 221 files with README bundled; `verge-cli` failed
  only on `verge-core ^0.4.0` not yet indexed.
- Sparse-index poll showed `"vers":"0.4.0"` for `verge-core` on the first
  poll before the CLI dispatch.
- `cargo install verge-cli --version 0.4.0 --locked` from a scratch directory
  installed `verge-cli v0.4.0`; the installed binary reports `verge 0.4.0`.
- Byte fidelity: both published `.crate` files were downloaded from
  `static.crates.io`, unpacked, and their `src/` diffed against
  `git archive v0.4.0` — zero differences in both crates.
